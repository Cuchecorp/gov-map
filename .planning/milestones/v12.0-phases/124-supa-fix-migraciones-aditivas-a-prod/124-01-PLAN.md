- **Aplicacion**: `set -a; source .env; set +a` y luego
  `PGCLIENTENCODING=UTF8 psql "$SUPABASE_DB_URL" --single-transaction -v ON_ERROR_STOP=1 -f <archivo>`.
  **JAMAS `supabase db push`. JAMAS `db reset`.** El valor de `SUPABASE_DB_URL` **nunca** se ecoa,
  expande, imprime ni escribe: solo aparece el **nombre** de la variable.
- **pgTAP post-apply**: `PGCLIENTENCODING=UTF8 psql "$SUPABASE_DB_URL" -tA -f supabase/tests/post-apply/<test>.sql`,
  **despues** de aplicar, **contra el schema aplicado**. Nunca contra el archivo.
- **Sin BOM**: los `.sql` se escriben en UTF-8 sin BOM (gotcha pagado: `psql` tropieza con el BOM).
- **CRLF**: `psql -tA` en este host emite `\r\n`. **Toda** canalizacion `psql -tA | sort | comm | grep -c`
  DEBE interponer `tr -d '\r'`. `sort -c` NO protege.
- **`set -o pipefail`** obligatorio en cualquier comando con pipe cuyo exit code se lea
  (`pnpm test | tail` sin el devuelve el status del `tail`).
- **Nada destructivo**: cero `DROP` de objeto con datos, cero cambio de tipo, cero backfill, cero
  cambio de firma. Si un fix lo exigiera → **parar** y escalar a `supabase-architect` + checkpoint
  blocking-human.
- **Cero deploy** (viaja con 125), **cero flip de flag `*_PUBLIC_ENABLED`**, **cero PII** (solo
  nombres de objeto/columna y agregados; jamas valores), **cero request a fuentes gubernamentales**,
  **cero instalacion de paquetes**.
- **Registro en el ledger**: tras aplicar, insertar la fila en `supabase_migrations.schema_migrations`
  por stdin/heredoc con `PGCLIENTENCODING=UTF8` (el ledger tiene hueco historico de 15 migraciones;
  se registra la nueva igual, sin intentar reconciliar el hueco).
- **Anti-secreto**: al citar patrones (cabeceras JWT, prefijos de key) usar **clases sin valor**
  (`<prefijo-JWT>`), jamas el literal. El grep anti-secreto ya mordio a tres executors.
- **Numeracion**: verificar con `ls supabase/migrations` (ultimo archivo = `0072`), **jamas** contra
